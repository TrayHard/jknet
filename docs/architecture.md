# Обзор архитектуры JKNet

Этот документ описывает устройство лаунчера JKNet: из каких частей он состоит, как они связаны, что лежит на диске и какие команды доступны фронтенду. Читатель — разработчик или ИИ-агент, который продолжает работу над лаунчером. Документ относится к ветке `main`: каркас репозитория, библиотека pk3, установка движков с запуском игры, браузер серверов, картинки карт, первый запуск, установщик Windows, обновление лаунчера и учётная запись на хабе JKNet.

## Компоненты

| Компонент | Технология | Ответственность |
| --- | --- | --- |
| Ядро | Rust, Tauri 2 | Файлы на диске, реестр Windows, настройки, будущие сеть и запуск игры |
| Фронтенд | React 19, TypeScript, Vite 8 | Экраны, состояние интерфейса, вызовы команд |
| Оформление | Tailwind CSS v4 | Токены из Figma, утилиты, типографика |
| Окно | WebView2 | Одно окно `main` без системного заголовка |

Фронтенд не имеет прямого доступа к файловой системе. Всё, что требует диска или реестра, проходит через команду ядра.

## Как компоненты взаимодействуют

1. `src-tauri/src/lib.rs` собирает приложение: подключает плагины, кладёт `AppState` в состояние Tauri, регистрирует команды.
2. Обработчик `setup` спрашивает у `app.path().app_local_data_dir()` папку конфигурации `%LOCALAPPDATA%\org.jknet.launcher`, переносит туда данные из старой папки `%LOCALAPPDATA%\JKNet` и вызывает `AppState::bootstrap`. Тот читает `settings.json` и создаёт папки данных. Функция не падает: лаунчер обязан открыть окно даже с нечитаемыми настройками.
3. React монтирует `App`, который поднимает `QueryClientProvider` и `HashRouter`.
4. Компонент вызывает хук из `src/lib/queries.ts`, хук вызывает обёртку из `src/lib/ipc.ts`, обёртка вызывает `invoke`.
5. Команда возвращает значение или `AppError`. Ошибка приходит на фронтенд строкой, её печатает `errorMessage`.

## Раскладка на диске

Папка конфигурации всегда `%LOCALAPPDATA%\org.jknet.launcher`. В ней лежит `settings.json`. Папки данных лежат там же. Настройка `dataDirOverride` переносит их по другому абсолютному пути.

Имя папки — идентификатор пакета из `src-tauri/tauri.conf.json`. Так отвечает `app.path().app_local_data_dir()`, и ту же папку удаляет деинсталлятор по флажку **Delete app data**. Программа при этом лежит в соседней `%LOCALAPPDATA%\JKNet`: имена развязаны намеренно, см. раздел [«Что собирает установщик»](#что-собирает-установщик).

```text
%LOCALAPPDATA%\org.jknet.launcher\
  settings.json
  clients\
    everyday\
      client.json        id, name, engineId, engineVersion, createdAt,
                         engineInstalledAt, enginePublishedAt, fsGame
      library.json       описания файлов библиотеки этого клиента
      engine\            файлы движка
      home\base\         fs_homepath клиента: конфиги, скриншоты, файлы pk3
      home\<fs_game>\    файлы pk3 для конкретного мода
  library\               скачанные pk3
  cache\                 списки серверов, релизы движков, ответы JKHub
    servers.json         последний удачный список серверов
    releases\<id>.json   список релизов движка и время загрузки
    downloads\           архивы движков, общие для всех клиентов
    levelshots\          картинки карт и index.json к ним
  logs\                  журналы tauri-plugin-log
```

Идентификатор клиента — slug имени: строчные ASCII-буквы, цифры и дефисы. Slug задаётся при создании и не меняется при переименовании: путь, который сохранила другая часть лаунчера, должен оставаться рабочим.

Папка игры остаётся только для чтения. Лаунчер проверяет наличие `base\assets0.pk3`–`assets3.pk3` и больше ничего в ней не трогает.

### Перенос из старой папки

Ранние сборки держали данные в `%LOCALAPPDATA%\JKNet`. Функция `migrate_legacy_root` из `src-tauri/src/paths.rs` переносит их один раз при запуске, до чтения настроек.

Функция переносит ровно пять записей: `settings.json`, `clients`, `library`, `cache`, `logs`. Каждую запись перемещает `fs::rename`. Если `rename` отказывает, например при переносе между дисками, функция копирует запись и удаляет оригинал. Остального содержимого старой папки она не касается: там лежат `JKNet.exe`, `uninstall.exe` и `resources\`, файлы установщика.

Перенос не начинается в четырёх случаях:

- старой папки нет;
- старая папка совпадает с новой;
- в старой папке нет ни одной из пяти записей;
- в новой папке уже есть `settings.json`, то есть лаунчер там уже работал.

Запись, которая уже есть в новой папке, остаётся в старой. Так обычно ведёт себя `logs`: старые сборки писали второй файл журнала в `app_log_dir()`, то есть в `logs\` внутри новой папки, и папка появлялась там до переноса. Журналы одноразовые, поэтому старый `logs\` просто остаётся на диске.

Ошибка переноса не останавливает запуск: сбойная запись попадает в журнал строкой `left in ...`. Удачный перенос даёт строку `migrated ... from ... to ...`. Если после переноса старая папка опустела, лаунчер удаляет её и пишет `removed the empty ...`. На машине с установленным лаунчером старая папка не опустеет: в ней лежит `JKNet.exe`.

Отчёт о переносе попадает в журнал позже самого переноса. Плагин журнала пишет в `logs\` внутри папки данных, а папку определяют настройки, которые читают после переноса. Поэтому `Migration` копит строки, а `lib.rs` отдаёт их в журнал сразу после подключения плагина.

## Поиск папки игры

Команда `detect_game_files` собирает кандидатов из трёх источников и снимает дубликаты по пути.

| Источник | Как ищет |
| --- | --- |
| `configured` | путь из `settings.json` |
| `steam` | `HKCU\Software\Valve\Steam\SteamPath`, затем `steamapps\libraryfolders.vdf`, затем папки `steamapps\common\*` с «jedi academy» в имени |
| `gog` | `HKLM\SOFTWARE\WOW6432Node\GOG.com\Games\*` с подходящим `gameName`, а также папки `C:\GOG Games\*` |

Кандидат отдаёт путь, источник, состояние четырёх архивов и флаг `valid`. Кандидат из сканирования попадает в список, только если все четыре архива на месте. Сохранённый путь показывается всегда, даже сломанный: иначе пользователь не поймёт, почему лаунчер не работает.

Команда `inspect_game_files` проверяет одну папку, выбранную в диалоге. Если пользователь указал корень установки, команда сама спускается в `GameData`.

### Как проходит обновление

Команда `refresh_servers` работает в три этапа.

1. Оба мастер-сервера опрашиваются одновременно, бюджет каждого — 1,5 с. Адреса сливаются в множество и теряют дубли. Мастер, который не прислал ни одной датаграммы, считается недоступным: `masterjk3.ravensoft.com` отвечает на DNS, но молчит, и пустой список от него нельзя путать с ответом «никто не играет».
2. Каждому адресу уходит `getinfo` со случайным `challenge`. Одновременно открыто не больше 64 сокетов, на попытку отводится 1 с, попыток две. Пинг строки — время обхода того запроса, на который пришёл ответ.
3. Серверы, которые не прислали ключ `g_humanplayers` и заявили хотя бы одного клиента, получают ещё и `getstatus`. Список игроков — единственное место, где на таком сервере отличают человека от бота. Правила — в разделе о реальных игроках.

Команда возвращает полный список и параллельно шлёт события. Аргумент `masters` заменяет пару стандартных мастер-серверов; пустой список означает «взять стандартные».

| Событие | Полезная нагрузка | Когда |
| --- | --- | --- |
| `servers:batch` | `{ servers: ServerInfo[] }` | раз в 100 мс, пока идёт опрос, и ещё раз после этапа 3 |
| `servers:done` | `{ total, responded, elapsedMs }` | один раз в конце |

Строки второго этапа приходят в браузер сразу, поэтому таблица заполняется, пока идёт третий этап. Уточнённые строки приходят одним пакетом `servers:batch` и заменяют прежние по адресу.

Ошибку команда возвращает только тогда, когда не ответил ни один мастер-сервер. Экран показывает плашку «Could not reach the master servers» с кнопкой **Retry** и продолжает показывать список из кеша.

### Реальные игроки и боты

Везде, где лаунчер показывает число игроков, это число людей. Боты идут отдельным числом и никогда не складываются с людьми. Причина видна в измерении на живой сети: из 235 клиентов на всех серверах людьми были 77, а 33 населённых сервера из 47 состояли из одних ботов.

Строка `ServerInfo` несёт три поля вместо одного.

| Поле | Смысл |
| --- | --- |
| `clients` | всё, что сервер считает клиентом, вместе с ботами. Единственное число, которое публикует ванильный сервер 1.01 |
| `humans` | реальные игроки. `null`, пока источник неизвестен |
| `bots` | боты среди `clients`. `null` рядом с неизвестным `humans` |
| `playersSource` | откуда взялось разделение: `info`, `status` или `unknown` |

Разделение выводится по трём правилам:

- Сервер прислал `g_humanplayers`. Значение становится полем `humans`, разность с полем `clients` — полем `bots`, источник равен `info`. Значение больше `clients` обрезается: оба ключа пишет один цикл движка, поэтому расхождение означает правку в моде.
- Сервер не прислал ключ, но заявил ноль клиентов. Разделение известно и так: `humans` и `bots` равны нулю, источник равен `info`.
- Сервер не прислал ключ и заявил хотя бы одного клиента. Разделение остаётся открытым до ответа на `getstatus`, источник равен `unknown`.

Ответ на `getstatus` разбирается по правилу пинга: игрок с пингом `0` — бот. Функция `SV_CalcPings` в файле `codemp/server/sv_main.cpp:868` пишет нулевой пинг только клиентам с флагом `SVF_BOT`. Клиент, который подключился, но ещё не вошёл в игру, получает `999`, а измеренный обход по сети занимает хотя бы миллисекунду. На движках, унаследовавших этот цикл из Quake 3, правило точное; для закрытого мода, который переписывает `cl->ping` вручную, оно остаётся эвристикой.

Поле `clients` после `getstatus` не меняется. Два числа считаются по разным спискам и могут расходиться: функция `SVC_Info` пропускает слоты `sv_privateClients`, функция `SVC_Status` их печатает, а очень длинный список игроков обрывается там, где кончается буфер движка в 1 КБ (`codemp/server/sv_main.cpp:432`). Для полей `humans` и `bots` побеждает счёт по списку игроков.

Третий этап опрашивает не больше 150 серверов за обновление, начиная с самых населённых. Одновременных сокетов столько же, сколько на втором этапе, бюджет ответа — 1,5 с.

Команда `get_server_status` помечает каждого игрока полем `isBot` по тому же правилу пинга. Панель сведений показывает ботов внизу списка, приглушённо и с бейджем **BOT**.

Экран **Servers** считает реальных игроков во всех числах: сортировка по умолчанию, фильтр **Players: Not empty**, счётчик в подзаголовке и список **Busiest servers** на экране **Home**. Фильтр **Bots: Hide bot-only** включён по умолчанию и убирает серверы, где `clients` больше нуля, а `humans` равно нулю. Когда в списке есть боты, подзаголовок дописывает «· K bots hidden from counts». Строка с неизвестным источником показывает число `clients` со знаком `?`: на таком сервере «кто-то играет» ближе к правде, чем ноль.

### Кеш, доверие, избранное

Удачное обновление пишет `cache\servers.json` вместе с полями `bots` и `playersSource`, поэтому результат третьего этапа переживает перезапуск лаунчера. Команда `get_cached_servers` читает этот файл и заново проставляет два флага, поэтому звезда, поставленная после последнего опроса, видна сразу. Нечитаемый кеш равносилен отсутствующему: следующее обновление перезапишет файл.

Кеш версии 0.1.1 не содержит двух добавленных полей. При чтении строка восстанавливает разделение из полей `clients` и `humans`, поэтому старый список не выглядит как список серверов, скрывающих свои числа. Строку, чей источник равен `status`, восстановление не трогает: поле `clients` такое разделение не воспроизводит.

Доверенные серверы лежат в ресурсе `src-tauri/resources/trusted_servers.json` и попадают в установщик через поле `bundle.resources`. Файл поставляется пустым массивом: комментарии в JSON невозможны, поэтому форма записи описана здесь.

```json
[
  {
    "address": "203.0.113.10:29070",
    "name": "EU FFA",
    "community": "JKHub",
    "url": "https://jkhub.org"
  }
]
```

Ключ `address` сравнивается с полем `address` строки точно, вместе с портом. Список читается один раз за запуск. Если ресурс отсутствует или сломан, ядро пишет предупреждение в журнал и работает с пустым списком.

Избранное и история живут в `settings.json`. Поле `favoriteServers` — массив адресов, поле `serverHistory` — массив записей `{ address, lastConnected }`, новые впереди, не длиннее 50 записей. Команда `set_server_favorite` переключает звезду, `add_server_history` записывает подключение. Обе возвращают целый документ настроек, чтобы фронтенд обновил свой кеш без второго вызова.

### Что проверено на живой сети

Проверку выполняет тест `talks_to_the_real_masters` в `src-tauri/src/servers/mod.rs`. Он помечен `#[ignore]`, потому что ходит в интернет.

```
cargo test --lib -- --ignored --nocapture talks_to_the_real_masters
```

Результат от 10 сентября 2026 г.: 232 адреса от мастер-серверов, 194 сервера ответили за 4,1 с. Второй тест `each_master_answers_on_its_own` показал, где взялись эти адреса: `master.jkhub.org` отдаёт 232 записи за 153 мс, `masterjk3.ravensoft.com` не отвечает вовсе и съедает весь свой бюджет в 1,5 с.

Третий тест `measures_the_bot_scan` меряет цену и отдачу этапа с `getstatus`.

```
cargo test --lib -- --ignored --nocapture measures_the_bot_scan
```

| Из них люди | 62–77 |

Обновление подорожало с 2,6 с до 4,1 с. Полторы секунды — это бюджет ответа на `getstatus`: этап заканчивается тогда, когда истекает срок у последнего молчащего сервера, а не тогда, когда ответил последний живой. Таблица заполняется по-прежнему за первые 2,6 с, третий этап уточняет счётчики уже на видимом списке.

Один запуск из четырёх получил от мастер-сервера всего 39 адресов вместо 234 и прошёл за 2,2 с. Это поведение самого мастер-сервера, а не этапа с `getstatus`: короткий ответ приходит целиком, вместе с маркером `\EOT`.
## Картинки карт

Панель сервера и герой-блок экрана **Home** показывают ту же картинку, что игра рисует в меню выбора уровня. Лаунчер не поставляет ни одного изображения: модуль `levelshots.rs` читает архивы, которые уже лежат у игрока, и складывает найденное в `cache\levelshots\`. Права на картинки принадлежат Raven Software и авторам карт, поэтому в установщик они не попадают.

Розничная игра держит 56 картинок в `base\assets0.pk3`, папка `levelshots\`; карты мультиплеера лежат в `levelshots\mp\`. Пользовательская карта везёт свою картинку в собственном pk3, обычно как `levelshots\<карта>.jpg`. Сообщества выпускают наборы картинок высокого разрешения, например «HQ Levelshots for SP/MP» на JKHub. Такой набор работает сам собой: это тот же pk3, и лаунчер читает его наравне с остальными.

### Ключ

Ключ индекса — имя карты строчными буквами, как его сообщает сервер: `mp/ffa1`, `mb2_smuggler`. Файловая система Quake 3 регистр не различает, а операторы серверов пишут `mapname` как придётся, поэтому одно написание выбирает функция `map_key` из `src-tauri/src/levelshots.rs`.

| Что приходит | Ключ | Откуда берётся |
| --- | --- | --- |
| `MP/FFA1` | `mp/ffa1` | ключ `mapname` в ответе `getinfo` |
| `mp\ffa1` | `mp/ffa1` | обратный слеш в имени карты |
| `maps/mp/ffa3.bsp` | `mp/ffa3` | сборка, которая сообщает имя файла целиком |
| `levelshots/MP/FFA1.JPG` | `mp/ffa1` | запись внутри pk3, разбирает `entry_key` |

Через `map_key` проходит и поле `map` строки сервера в `servers/mod.rs`. Строка браузера, фильтр по карте, кеш `servers.json` и картинка получают одно значение, а не четыре написания одного имени.

### Источники и порядок

Индекс собирают по тем же правилам, по которым движок выбирает файл. Функция `FS_AddGameDirectory` (`codemp/qcommon/files.cpp:3078`) кладёт саму папку в путь поиска раньше её архивов, а каждый архив — впереди предыдущего. Значит, отвечает последний архив по порядку `paksort`, а свободно лежащий файл проигрывает любому архиву той же папки.

Модуль читает источники в порядке «побеждает последний»:

1. Свободные файлы в `<GameData>\base\levelshots\`, затем архивы `<GameData>\base\*.pk3` в порядке `paksort`.
2. Для каждого клиента по алфавиту слага — то же самое в каждой папке мода: `clients\<slug>\home\base\`, `clients\<slug>\home\<fs_game>\` и остальных папках внутри `home\`.

Порядок `paksort` берёт готовая функция `pak_order` из `library.rs`: тот же регистронезависимый порядок имён с `dl_` в конце. Все папки внутри `home\` читаются подряд, а не только `fs_game` клиента: перечислить папки дешевле, чем держать вторую копию правила, которое выбирает `fs_game`.

### Индекс и кеш

```text
cache\levelshots\
  index.json        что нашлось и в каких файлах
  mp__ffa1.jpg      картинка карты mp/ffa1
  mb2_smuggler.png  картинка карты mb2_smuggler, переделанная из TGA
```

Картинки лежат плоско, слеш ключа записан как `__`. Имя файла собирает `cache_file_name`: она отклоняет ключ с `..`, с пустым сегментом и с любым символом вне `a-z`, `0-9`, `_`, `-`, `.`, `+`. Записи внутри pk3 приходят из архива, который собрал незнакомый человек, поэтому папка кеша не должна получить от него ни подпапку, ни путь наружу.

Документ `index.json` хранит три поля.

| Поле | Что в нём |
| --- | --- |
| `builtAt` | время последней полной пересборки, RFC 3339 в UTC |
| `sources` | прочитанные файлы: `path`, `mtime` в секундах Unix, `size` |
| `maps` | ключ → `{ file, source, width, height }` |

Пересборка идёт, когда индекса нет, когда он не читается и когда список `sources` разошёлся с диском: файл изменился, исчез или появился новый pk3. В остальных случаях лаунчер берёт готовый индекс, а проверка стоит одного `metadata` на источник.

Работу выполняет `spawn_blocking`: чтение архива на 561 МБ и перекодирование картинки блокируют поток, а рантайм обязан отвечать остальному лаунчеру. JPEG и PNG в пределах 1024 пикселей по длинной стороне копируются байт в байт: пережимать розничный `levelshot` 512×512 значит только портить его. Картинку крупнее модуль уменьшает до 1024 пикселей, а TGA переделывает в PNG всегда, потому что TGA не читает ни один браузер. Запись длиннее 32 МБ пропускается: `levelshot` такого размера не существует, а поддельный pk3 существует.

Пересборка удаляет из папки картинки, на которые больше не указывает ни один ключ. Отказ записи или удаления стоит одной карты и попадает в журнал: файл, который показывает окно, Windows держит занятым, и это не повод обрывать всю пересборку.

### Промах и точечный поиск

Команда `get_levelshot` отвечает в три шага.

1. Приводит индекс в актуальное состояние по правилам выше.
2. Отдаёт запись индекса, если она есть и файл на месте.
3. На промахе ищет `levelshots/<ключ>.jpg|jpeg|png|tga` прямо в источниках, дописывает найденное в индекс и отдаёт.

Третий шаг закрывает случай, ради которого он написан: игрок положил pk3 с картой минуту назад, индекс по своим правилам ещё актуален, а карта в нём не значится. Точечный поиск читает только центральный каталог каждого архива и распаковывает не больше одной записи.

Ключ, которого нет нигде, запоминается в памяти до следующей пересборки. Без этого список из двух сотен серверов с чужими картами открывал бы центральный каталог `assets0.pk3` две сотни раз. Одновременный вызов защищён асинхронным замком в `LevelshotState`: десять карточек, которые смонтировались разом, вызывают одну пересборку, а не десять.

### Как картинка попадает в окно

Файл отдаёт протокол ресурсов Tauri. Раздел `app.security.assetProtocol` файла `tauri.conf.json` включает его и ограничивает областью `$APPLOCALDATA/cache/levelshots/**`. Область статична, а `dataDirOverride` уводит папку данных куда угодно, поэтому обработчик `setup` дополнительно вызывает `levelshots::allow_cache_folder`: та добавляет в область уже разрешённый путь. Крейт `tauri` собран с признаком `protocol-asset` — без него обработчик протокола не регистрируется.

Разрешения в `capabilities/default.json` протокол не требует: областью управляет только конфигурация.

Фронтенд превращает путь в адрес функцией `levelshotUrl` из `src/lib/ipc.ts`, обёрткой над `convertFileSrc`. На Windows адрес выглядит как `http://asset.localhost/<путь>`, на остальных системах — как `asset://localhost/<путь>`. Политика CSP не задана (`"csp": null`). Когда её зададут, директива `img-src` обязана разрешить `asset:` и `http://asset.localhost`, иначе картинки перестанут грузиться молча.

### Событие

После каждой пересборки ядро шлёт событие `levelshots:changed` без тела. Хук `useLevelshotEvents` из `src/lib/queries.ts` подписан на него в компоненте `GameEventsProvider` и сбрасывает кеш React Query по префиксу ключа `levelshots`. Так карта, у которой минуту назад картинки не было, получает её на открытом экране.

### Что показывает интерфейс

| Место | Компонент | Что рисует |
| --- | --- | --- |
| Панель сведений экрана **Servers** | `MapPreview` | картинка карты выбранного сервера |
| Герой-блок экрана **Home** | `MapPreview` | карта сервера из первой записи `serverHistory`, если он есть в кеше списка |
| Карточка **Cache** экрана **Settings** | `MapPicturesCard` | число карт с картинкой и кнопка **Rebuild** |

Компонент `MapPreview` из `src/components/MapPreview.tsx` рисует градиент со значком карты, пока ответа нет и когда ответ равен `null`. Заглушка — обычное состояние, а не ошибка: у половины пользовательских карт картинки нет вовсе. Подпись с именем карты стоит и на картинке, и на заглушке.

Строки таблицы серверов остаются текстовыми. Миниатюра 40×24 в строке возможна и стоит одного вызова `get_levelshot` на строку, но список из двух сотен строк тогда открывает два десятка архивов на первой же прокрутке.

### Что проверено

Тест `indexes_the_retail_archives` в `src-tauri/src/levelshots.rs` собирает индекс из настоящей установки. Он помечен `#[ignore]`, потому что знает путь, который есть на одной машине.

```

```

### Частичное обновление настроек

Команда `update_settings` принимает патч, а не целый документ. Аргумент `patch` несёт только изменённые поля. Ядро читает `settings.json` заново, накладывает присланные поля, записывает файл и возвращает целый документ.

| Поле патча | Поля пропущено | Поле прислано со значением | Поле прислано как `null` |
| --- | --- | --- | --- |
| `gameDataPath`, `defaultClientId`, `dataDirOverride` | значение сохраняется | значение записывается, пустая строка равна `null` | значение очищается |
| `closeOnLaunch`, `extraLaunchArgs`, `favoriteServers`, `serverHistory`, `onboardingCompleted` | значение сохраняется | значение заменяется целиком | `null` не принимается |

Контракт закрывает потерю правок. Фронтенд держит настройки в кеше React Query, и отправка этого кеша целиком затирала поля, изменённые другим писателем: правка `extraLaunchArgs` в `settings.json` при открытом лаунчере пропадала на первой же записи с экрана **Clients**. Нечитаемый файл откатывает запись на копию в памяти и даёт предупреждение в журнал: одна сломанная строка не должна блокировать все настройки.

Команды `set_server_favorite`, `add_server_history` и `delete_client` тоже читают файл перед записью, а не берут копию из памяти.

Имя поля вне списка ядро отклоняет: опечатка в `camelCase` на фронтенде обязана падать громко, а не записывать пустоту.

### Изменение клиента

Команда `update_client` меняет имя клиента и его папку мода. Аргумент, которого нет в вызове, сохраняет значение. Пустая строка в `fsGame` очищает поле, и клиент возвращается к папке по умолчанию своего движка.

Значение `fsGame` проходит проверку на одно простое имя папки: латинские буквы, цифры, `_`, `-`, `+`, не длиннее 64 символов. Разделитель пути, двоеточие и `..` отклоняются вариантом `AppError::InvalidInput`. Значение уходит движку как `+set fs_game` и становится папкой внутри `home\`, поэтому оно обязано остаться именем, а не путём.

Slug клиента не меняется при переименовании: путь, который сохранила другая часть лаунчера, должен остаться рабочим.

## Библиотека pk3

Файл библиотеки принадлежит клиенту, а не лаунчеру. Модуль `library.rs` работает только с папкой `clients\<slug>\home\`: движок получает её как `fs_homepath`, поэтому лаунчер устанавливает файлы, ничего не записывая в папку игры.

Источник истины — диск. Команда `list_library` перечисляет `home\*\*.pk3` и `home\*\*.pk3.disabled`, сверяет находки со справочником `library.json` и дописывает недостающие записи, прочитав архив. Справочник хранит только то, чего нет в архиве: имя на карточке, происхождение файла и заметки. Удалите `library.json` — лаунчер соберёт его заново и потеряет лишь имена.

Идентификатор файла — `<папка>/<имя файла>`, например `base/kyle.pk3`. Имя всегда записано во включённом виде, поэтому идентификатор переживает переключение тумблера.

### Два правила движка

Устройство модуля задают две строки `codemp/qcommon/files.cpp` (OpenJK, ветка `master`, коммит `1a6a6434`).

| Правило | Код | Следствие для лаунчера |
| --- | --- | --- |
| Движок берёт только расширение `.pk3` | `files.cpp:3089` | Переименование в `имя.pk3.disabled` выключает файл, не удаляя его. Так работает тумблер на карточке |
| Список сортирует `paksort`, каждый архив встаёт в начало пути поиска | `files.cpp:3025`, `files.cpp:3152` | При совпадении внутреннего пути выигрывает архив, который сортируется последним. Имена с префиксом `dl_` идут после всех остальных |

Команда `find_library_conflicts` повторяет обе строки: она сравнивает содержимое включённых архивов одной папки и называет победителя. Ответ ограничен первыми 200 путями и кешируется по набору файлов, их размерам и времени изменения, потому что открыть два десятка архивов стоит сотни миллисекунд.

### Категории

Команда `inspect_pk3` открывает архив на чтение и определяет категорию по внутренним путям. Порядок проверок — приоритет, а не предпочтение.

| Категория | Признак | Почему в этом месте |
| --- | --- | --- |
| `mod` | любой `.dll` или `.qvm` | Двоичный модуль делает архив модом, какие бы ресурсы с ним ни ехали |
| `map` | `maps/*.bsp` | Однозначный признак карты |
| `skin` | `models/players/` | Самый частый вид файла |
| `hilt` | `models/weapons2/saber*` или `ext_data/sabers/*.sab` | Рукоятка редко приезжает вместе со скином |
| `hud` | `gfx/hud/` или `ui/*.menu` | — |
| `sound` | не меньше 60 % записей в `sound/` или `music/` | Отдельные звуки везут половина сборок, поэтому нужна доля, а не факт |
| `other` | всё остальное | — |

Проверка на реальном архиве: `assets1.pk3` из установки Steam (652 804 510 байт, 7973 записи) получает категорию `skin` и верхний уровень `botfiles`, `effects`, `ext_data`, `fffx`, `fonts`, `forcecfg`, `gfx`, `menu`, `models`, `shaders`, `textures`, `ui`. Тест `library::tests::inspects_a_real_asset_archive` помечен `#[ignore]` и запускается вручную.

### Отказы при установке

Команда `add_library_files` копирует файлы в `home\<папка>\` и возвращает два списка: что установлено и что пропущено с причиной. Лаунчер не перезаписывает существующий файл: одинаковые байты под другим именем — это дубликат, а одинаковое имя с другими байтами — столкновение. В первом случае ответ называет уже установленный файл, во втором предлагает свободное имя вида `map_2.pk3`.

### Событие

После каждого изменения ядро шлёт событие `library:changed` с телом `{ clientId }`. Экран **Library** подписан на него и перечитывает список: так изменение доходит до открытого экрана, даже если его сделала другая часть лаунчера.

## Установка движка

Движок приходит из релизов GitHub. Модуль `engines.rs` хранит реестр, модуль `engine_install.rs` выполняет работу.

Данные проверены 10 сентября 2026 г. запросом к `https://api.github.com/repos/<владелец>/<репозиторий>/releases?per_page=10` и распаковкой архива.

| Движок | Репозиторий | Новейший релиз | Архив для Windows x86 | Исполняемый файл |
| --- | --- | --- | --- | --- |
| OpenJK | `JACoders/OpenJK` | `latest`, скользящий | `OpenJK-windows-x86.zip` | `openjk.x86.exe` |
| EternalJK | `eternalcodes/EternalJK` | `1.5.8.5` от 2020-06-15 | `eternaljk-win32-portable.zip` | `eternaljk.x86.exe` |
| TaystJK | `taysta/TaystJK` | `latest`, скользящий | `TaystJK-windows-x86.zip` | `taystjk.x86.exe` |
| jaMME | `entdark/jaMME` | `latest`, скользящий | `jamme-windows-x86.zip` | `jamme.exe` |

Архив выбирает список правил `AssetRule`: набор обязательных и набор запрещённых подстрок, регистр не учитывается. Правила проверяются по порядку, побеждает первое сработавшее. Два случая, ради которых правила существуют: релиз OpenJK содержит архивы `OpenJO-*` для другой игры, а TaystJK публикует сборку `-AddressSanitizer` для отладки.

Установка идёт тремя шагами:

1. Команда `list_engine_releases` читает до десяти релизов и оставляет те, где есть архив для Windows. Ответ живёт 10 минут в памяти и в файле `cache\releases\<id>.json`. Если GitHub недоступен, ядро отдаёт устаревший файл и пишет предупреждение в журнал.
2. Команда `install_engine` скачивает архив в `cache\downloads\<id>-<tag>.zip`. Файл нужного размера переиспользуется: один архив обслуживает все клиенты на этом движке. Загрузка идёт потоком в файл `.part`, и целевое имя файл получает только после конца потока. Поток пишет `tokio::fs`: блокирующая запись между двумя `await` заняла бы рабочий поток рантайма на каждый кусок архива.
3. Распаковка очищает `clients\<slug>\engine\` и заполняет её заново. Если архив завёрнут в одну папку верхнего уровня, папка убирается. После распаковки ядро проверяет, что исполняемый файл на месте, и записывает в `client.json` поля `engineVersion`, `engineInstalledAt` и `enginePublishedAt`.

Каждая запись архива проходит проверку на выход за пределы папки: абсолютный путь, префикс диска и любой `..` отклоняют весь архив. Это защита от атаки zip slip.

Токен авторизации ядро не отправляет. Анонимный лимит GitHub — 60 запросов в час на адрес, кеш на 10 минут укладывается в него с запасом. Ответ 403 или 429 с заголовком `x-ratelimit-remaining: 0` превращается в вариант `AppError::RateLimited` с указанием, через сколько минут лимит снимется. Проверку проходят оба запроса: и список релизов, и архив. Архив обычно отдаёт CDN за пределами `api.github.com`, где лимит не действует, но перенаправление обратно к API существует, и ответ на него обязан читаться как ожидание, а не как битая ссылка.

### Одна установка на клиент

Ядро держит множество занятых `clientId` в состоянии `InstallState`, которое лежит рядом с `AppState` и `LaunchState`. Второй вызов `install_engine` для того же клиента возвращает `AppError::Busy` и не трогает ни архив, ни папку `engine\`. Событие о такой ошибке не отправляется: оно заменило бы полосу прогресса идущей установки сообщением, которого игрок не вызывал. Разные клиенты ставятся одновременно.

Без замка два быстрых нажатия **Install engine** запускали две установки: обе писали в один файл `<id>-<tag>.zip.part`, обе вызывали `remove_dir_all` для одной папки `engine\` и заново заполняли её. Результат — папка из половин двух сборок, клиент не запускается до переустановки.

Замок снимается и после успеха, и после ошибки. На фронтенде кнопки **Install engine**, **Update to `TAG`** и **Check updates** выключены, пока установка этого клиента идёт: карточка следит и за событием прогресса, и за состоянием `isPending` самой мутации, потому что первое событие приходит уже после ответа ядра.

Команда `check_engine_update` сравнивает установленный тег с новейшим. Три проекта из четырёх публикуют скользящий тег `latest`, который не меняется, поэтому при равных тегах решает время публикации релиза. Клиент, записанный до появления поля `enginePublishedAt`, обновление не предлагает: иначе кнопка горела бы всегда.

## Запуск игры

Модуль `launch.rs` запускает исполняемый файл движка сам. Steam в цепочке не участвует, папка игры остаётся только для чтения.

### Три корня файловой системы

Движок из ветки Quake 3 ищет файлы в трёх корнях и предпочитает тот, что добавлен последним (`codemp/qcommon/files.cpp`, функция `FS_Startup`).

| Cvar | Значение | Что там лежит |
| --- | --- | --- |
| `fs_cdpath` | папка `GameData` игрока | `base\assets0.pk3`–`assets3.pk3` |
| `fs_basepath` | `clients\<slug>\engine` | распакованная сборка движка |
| `fs_homepath` | `clients\<slug>\home` | конфиги, скриншоты, загрузки |

Раскладка выбрана так не случайно. Каждый движок кладёт в архив свои `base\cgamex86.dll`, `uix86.dll` и `jampgamex86.dll`, и они обязаны победить модули версии 1.01 из розничной папки `base`. Писать в папку игры лаунчер не имеет права, значит движок туда не скопировать. Указание `fs_basepath` на распакованную сборку, а `fs_cdpath` на игру даёт движку и свои модули, и ассеты игрока. Cvar `fs_copyfiles` остаётся равным 0, поэтому обратно в папку игры ничего не пишется.

**Примечание.** Значение `fs_game` берётся из поля `fsGame` клиента, а если оно пустое — из движка. У jaMME значение по умолчанию `mme`: сборка живёт в подпапке `mme\`, что подтверждает файл `start_jaMME.cmd` внутри архива. Поле `fsGame` задаёт диалог **Client settings** на экране **Clients**, его открывает кнопка с шестерёнкой на карточке.

### Порядок аргументов

Функция `build_launch_args` собирает список токенов. Каждый токен — отдельный элемент списка: экранированием кавычек занимается `std::process::Command`, а строка, собранная вручную, ломается на первом же пути с пробелом.

1. `+set fs_cdpath`, `+set fs_basepath`, `+set fs_homepath`.
2. `+set fs_game`, если значение непустое.
3. Токены из настройки `extraLaunchArgs`, разобранные как командная строка: пробел разделяет, двойные кавычки держат группу вместе.
4. Токены аргумента `extraArgs` команды.
5. `+connect ADDRESS`, если адрес передан.

Настройку `extraLaunchArgs` задаёт поле **Extra launch arguments** на экране **Settings**. Аргумент `extraArgs` команды `launch_client` живёт один запуск и в настройках не сохраняется.

Адрес с пробелом отклоняется вариантом `AppError::InvalidInput`: `+connect` принимает один токен, а пробел превратил бы остаток в отдельные команды консоли.

### Один процесс за раз

Состояние `LaunchState` хранит дочерний процесс отдельно от `AppState`: дескриптору процесса нечего делать за замком настроек. Второй запуск отклоняется, пока первый жив. Поток-наблюдатель опрашивает процесс каждые 500 мс и после выхода шлёт событие. Опрос вместо `wait()` нужен потому, что тот же дескриптор должен оставаться доступным команде `stop_game`.

### События

Аргументы Rust приходят на фронтенд в `camelCase`, как и у команд.

| Событие | Полезная нагрузка | Когда |
| --- | --- | --- |
| `launch:engine-install-progress` | `clientId`, `phase`, `downloaded`, `total`, `message` | во время установки движка, не чаще одного раза в 150 мс |
| `launch:game-started` | `clientId`, `pid` | сразу после запуска процесса |
| `launch:game-exited` | `clientId`, `exitCode` | после выхода процесса, как бы он ни завершился |

Поле `phase` принимает значения `download`, `extract`, `done` и `error`.

Фронтенд подписывается один раз, в компоненте `GameEventsProvider` над маршрутизатором: установка движка обязана пережить переход между экранами. Если настройка `closeOnLaunch` включена, обработчик `launch:game-started` прячет окно, а `launch:game-exited` показывает его снова.

## Первый запуск

Три шага первого запуска доводят игрока от пустого лаунчера до рабочей кнопки **Play**: папка игры, первый клиент, учётная запись. Экран лежит в `src/pages/onboarding/`, ядро для него получило одно поле настроек и ни одной команды.

Настройка `onboardingCompleted` решает, показывать шаги или нет. Поле лежит в `settings.json`, по умолчанию равно `false` и принимает патч, как остальные булевы поля. Файл настроек, записанный до появления поля, читается как «шаги не пройдены»: лаунчер, который не может доказать обратное, показывает настройку.

Компонент `OnboardingGate` стоит над `AppShell` и перенаправляет на `#/onboarding` любой другой маршрут, пока флаг равен `false`. Экран рисуется без боковой панели, заголовок окна остаётся на месте и остаётся перетаскиваемым. Ошибка чтения настроек пропускает игрока дальше: она не говорит, проходил ли он шаги, а экраны печатают её сами.

### Номер шага выводится, а не хранится

Лаунчер не запоминает, на каком шаге его закрыли. Функция `initialStep` из `src/pages/onboarding/steps.ts` считает номер по тому, что уже настроено.

| Состояние настроек | Шаг |
| --- | --- |
| `gameDataPath` пуст | 1 |
| `gameDataPath` задан, клиента по умолчанию с установленным движком нет | 2 |
| клиент по умолчанию есть, и у него заполнено `engineVersion` | 3 |

Хранимый номер отправил бы игрока, который удалил единственный клиент, на экран учётной записи, где играть нечем.

### Что делает каждый шаг

1. Папка игры. Команда `detect_game_files` даёт карточки-переключатели: источник, путь и состояние четырёх архивов. Сломанный кандидат тоже попадает в список и называет недостающие файлы. Кнопка выбора папки проверяет её командой `inspect_game_files` и добавляет к списку, не заменяя его. Кнопка **Continue** активна только при годном выборе и сохраняет `gameDataPath` патчем.
2. Первый клиент. Карточки движков показывают название, новейший тег, размер архива, описание и признак **Recommended**. Кнопка **Continue** делает всю работу: `create_client`, патч `defaultClientId`, `install_engine`. Полоса прогресса идёт за событием `launch:engine-install-progress`, а конец установки переводит на третий шаг. Ошибка оставляет клиент на месте и даёт **Retry** и **Skip download**: движок ставится позже на экране **Clients**. Если клиенты уже есть, первым вариантом идёт **Use existing client**.
3. Учётная запись. Кнопки **Continue with JKHub** и **Continue with Discord** начинают вход через браузер, описанный в разделе [«Учётная запись и хаб»](#учётная-запись-и-хаб). Кнопка **Skip, play as guest** ставит `onboardingCompleted` в `true` и открывает **Home**. Шаг не блокирует: кнопка гостя остаётся на месте и после отказа провайдера.

Список релизов на втором шаге спрашивается у всех движков сразу, и ответ ждут не дольше 3 с. Карточка без ответа печатает `latest`, что верно для трёх проектов из четырёх. Хук `useEngineVersions` не задерживает кнопку **Continue**: недоступный GitHub не мешает создать клиент.

Кнопка **Run first-time setup again** в карточке Launch экрана **Settings** сбрасывает флаг и открывает `#/onboarding`. Ничего не удаляется. Шаги выводятся из настроек, поэтому пройденная настройка открывается сразу на третьем шаге.

## Учётная запись и хаб

Хаб JKNet — отдельная служба на HTTPS. Лаунчер разговаривает с ней по JSON и держит на ней учётную запись игрока, список друзей, присутствие и приглашения на сервер. Контракт называется API v1. Модуль `src-tauri/src/hub/` реализует всю сторону лаунчера, модуль `src-tauri/src/account.rs` — команды входа и владения учётной записью.

Саму службу пишет отдельная ветка. Лаунчер собран по контракту и проверен на заглушке `scripts/mock-hub.mjs`.

### Вход через браузер

Провайдеры входа — JKHub и Discord, оба по OAuth 2.0 с PKCE. Ни один из них не выдал OAuth-клиента, поэтому хаб отвечает на запрос сессии кодом `provider_error`, а лаунчер печатает «JKHub sign-in is not available yet» и оставляет кнопку **Skip, play as guest**.

Схема входа не содержит ни собственной ссылки вида `jknet://`, ни слушающего порта. Лаунчер спрашивает у хаба сессию, открывает её адрес в системном браузере и опрашивает сессию, пока провайдер не вернёт игрока обратно.

```text
фронтенд            ядро                       хаб                браузер
   | begin_sign_in    |                         |                    |
   |----------------->| POST /v1/auth/login-sessions                  |
   |                  |------------------------>|                    |
   |                  |<-- id, url (pending) ---|                    |
   |                  |------- открыть url ----------------------->  |
   |<-- sessionId ----|                         |<--- авторизация ---|
   | poll_sign_in     |                         |                    |
   |----------------->| GET /v1/auth/login-sessions/{id}             |
   |                  |------------------------>|                    |
   |<-- pending ------|<-- pending -------------|                    |
   |   (каждые 2 с)   |                         |                    |
   |----------------->|------------------------>|                    |
   |<-- done, user ---|<-- done, token, user ---|                    |
```

Ни одна ссылка не открывается вслепую. Команда `begin_sign_in` проверяет адрес от хаба функцией `is_http_url`: схема `file:` или `javascript:` в этом поле превратила бы взломанный хаб в запуск кода на машине игрока.

Опросом занимается хук `useSignIn` из `src/lib/queries.ts`. Интервал — 2 с, бюджет — 10 мин, как срок жизни сессии в контракте. Второй опрос не стартует, пока не ответил первый.

Токен хаб отдаёт ровно один раз, на первом чтении сессии со статусом `done`. Команда `poll_sign_in` записывает его в `settings.json` до того, как ответит фронтенду: лаунчер, закрытый в момент появления имени на экране, остаётся с рабочим входом.

### Где живёт токен

Токен не пересекает границу IPC. Он лежит в `settings.json` в поле `hubToken`, ядро ставит его в заголовок `Authorization` и вырезает из любого ответа команды методом `Settings::redacted`. Так отвечают `get_settings`, `update_settings`, `set_server_favorite` и `add_server_history`.

Фронтенду вместо токена доступна команда `get_account_state`: есть ли токен, кому он принадлежит, какой адрес у хаба и местный ли он. Тип `HubContext` печатает `<redacted>` вместо токена, поэтому `{:?}`, добавленный в журнал при поиске ошибки, не выносит секрет в `jknet.log`.

### Поля настроек

| Поле | Тип | Значение по умолчанию | Что задаёт |
| --- | --- | --- | --- |
| `hubUrl` | строка | `http://127.0.0.1:8787` | адрес хаба без завершающей косой черты |
| `hubToken` | строка или `null` | `null` | токен входа, 64 шестнадцатеричных символа |
| `hubUser` | объект или `null` | `null` | учётная запись, как её описал хаб в последний раз |

Реализация `Default` для `Settings` написана вручную, а не выведена макросом: у поля `hubUrl` значение по умолчанию отличается от пустой строки. Атрибут `#[serde(default)]` на структуре берёт недостающие поля именно из этой реализации, поэтому `settings.json`, записанный до появления хаба, читается как «хаб для разработки».

Патч с адресом хаба проходит проверку `SettingsPatch::validate`. Адрес без схемы `http://` или `https://` отклоняется вариантом `AppError::InvalidInput` в момент правки. Записанный адрес ломал бы каждый следующий вызов, и жалоба приходила бы не туда, где сделана опечатка. Пустая строка возвращает поле к значению по умолчанию.

### Ошибки

Хаб отвечает на отказ документом `{"error":{"code","message"}}`. Коды контракта: `not_found`, `unauthorized`, `forbidden`, `invalid`, `conflict`, `rate_limited`, `provider_error`, `internal`. Вариант `AppError::Hub { code, message }` хранит код и печатается как `hub КОД: СООБЩЕНИЕ`.

Код входит в строку намеренно. `AppError` доходит до фронтенда одной строкой, а экранам коды нужно различать: `provider_error` означает «JKHub ещё не выдал OAuth-клиента, оставьте кнопку гостя», а `conflict` на том же экране означает «имя занято, наберите другое». Функция `hubErrorCode` из `src/lib/ipc.ts` читает префикс обратно, функция `hubErrorMessage` его убирает для показа.

Ответ, который не похож на контракт, тоже получает код: его выводят из статуса HTTP. Так экран никогда не отличает «кода нет» от «код мне незнаком».

### Сеть

| Правило | Значение |
| --- | --- |
| Таймаут запроса | 10 с вместе с подключением |
| Повтор | один, и только когда соединение отказано или сброшено |
| Пул соединений | один `HubClient` в состоянии Tauri |

Повтор намеренно узкий. Хаб, который ответил отказом, решение принял, а POST, который до него дошёл, нельзя отправлять дважды. Поэтому повторяется только запрос, чей сокет не унёс ни байта: так выглядит хаб, перезапущенный под работающим лаунчером.

Адрес и токен не заморожены в клиенте, а собираются из настроек в момент вызова структурой `HubContext`. Игрок меняет их входом, выходом и полем **Hub address**, и ни одно из этих действий не должно требовать перезапуска.

Файл `src-tauri/capabilities/default.json` учётная запись не меняет. Браузер открывает ядро вызовом `opener().open_url` из Rust, а область разрешений проверяет только команды, которые пришли из webview. Схему адреса вместо неё проверяет функция `is_http_url`. Разрешение `opener:default` уже в списке и покрывает схемы `http` и `https` для вызовов с фронтенда.

### Событие

| Событие | Полезная нагрузка | Когда |
| --- | --- | --- |
| `account:changed` | `{ signedIn }` | после входа, выхода, переименования и удаления учётной записи |

Хук `useAccountState` подписывается на событие и сбрасывает кеш учётной записи и настроек. Так выход, сделанный на экране **Settings**, доходит до боковой панели.

### Экран Friends и общий модуль

Модуль `hub/` реализует контракт целиком, включая друзей, присутствие и приглашения. Вызывающей стороны у этой половины пока нет: её добавит экран **Friends**. Объявление модуля в `lib.rs` несёт атрибут `#[allow(dead_code, unused_imports)]` с комментарием об этом.

Половины написаны вместе намеренно. Второй клиент означал бы второе место, где к запросу приклеивают токен.

### Чем настоящий хаб отличается от контракта

Службу пишет отдельная ветка, и в трёх местах она уточняет контракт там, где он молчит. Лаунчер учитывает все три.

- Поля `token` и `user` в ответе `GET /v1/auth/login-sessions/{id}` отсутствуют целиком, пока сессия не `done`, и исчезают после первой выдачи токена. Контракт описывал их как `null`. Структура `LoginSession` объявляет оба поля с атрибутом `#[serde(default)]`, поэтому отсутствие поля читается как `None`. Повторное чтение сессии со статусом `done` без токена не ошибка: команда `poll_sign_in` отвечает уже записанной учётной записью.
- Форма провайдера `dev` отправляет `GET /v1/auth/dev/callback?state=…&name=…`. Кода авторизации у этого провайдера нет, поэтому вместо `code` идёт имя. Лаунчера это не касается: он открывает адрес из поля `url` и опрашивает сессию. Заглушка повторяет ту же форму и тот же адрес callback.
- Событие `me.updated` после `PATCH /v1/me` приходит только владельцу токена. Друзья узнают новое имя из `GET /v1/friends`, который экран **Friends** и так опрашивает раз в 30 с. Рассылать `me.updated` друзьям нельзя: получатель принял бы чужой профиль за свой.

Остальные отклонения касаются друзей, присутствия и приглашений. Их учтёт экран **Friends**, у которого эта половина контракта появится вместе с вызывающей стороной.

### Заглушка хаба

Файл `scripts/mock-hub.mjs` отвечает за хаб, пока службы нет. Он написан на Node без зависимостей, держит всё в памяти и реализует ту часть API v1, которой пользуется вход.

```text
node scripts/mock-hub.mjs
node scripts/mock-hub.mjs --port 8799
```

Провайдер `dev` показывает по адресу сессии ту же форму имени, что и настоящий хаб, и завершает вход по адресу `/v1/auth/dev/callback?state=…&name=…`. Браузер, открывший форму, отменяет таймер: имя из формы побеждает. Сессия, которую браузер не открыл, завершается сама через 3 с — так тесту не нужен ни браузер, ни человек. JKHub и Discord отвечают `503 provider_error`. Переменные окружения `MOCK_HUB_PROVIDERS`, `MOCK_HUB_DEV_DELAY_MS` и `MOCK_HUB_TAKEN_NAME` меняют это поведение. Полное описание — в комментарии в начале файла.

Тесты `hub::mock_tests` запускают заглушку дочерним процессом и проходят вход целиком: сессия, опрос, чтение учётной записи, переименование, список друзей, выход. Они помечены `#[ignore]`, потому что требуют Node в `PATH` и свободного порта.

```text
cargo test --lib -- --ignored --nocapture hub::mock_tests
```

Результат от 10 сентября 2026 г.: четыре теста проходят за 4,1 с.

| Место | Что нового |
| --- | --- |
| Третий шаг первого запуска | Кнопки провайдеров работают, ожидание браузера с кнопкой **Cancel**, после входа имя и кнопка **Continue** |
| Боковая панель | Блок игрока показывает имя и аватар, а без входа — **Guest**; нажатие открывает `#/settings?section=account` |

Кнопка **Developer sign-in** появляется только тогда, когда `hubUrl` указывает на эту машину. Проверку делает функция `is_local_hub`: она разбирает адрес и сравнивает узел с `localhost` или петлевым IP-адресом. Сравнение по префиксу не годится, потому что имя `127.0.0.1.attacker.example` разрешает его владелец.

## Установщик и обновление лаунчера

Игрок скачивает один файл и больше на страницу загрузки не возвращается: установленный лаунчер обновляет себя сам. Команд IPC этот механизм не добавляет. Работу делают два плагина Tauri, `tauri-plugin-updater` и `tauri-plugin-process`. Фронтенд вызывает их напрямую через пакеты `@tauri-apps/plugin-updater` и `@tauri-apps/plugin-process`.

### Что собирает установщик

Раздел `bundle` файла `src-tauri/tauri.conf.json` задаёт единственную цель `nsis`. Формата `msi` в списке нет намеренно: WiX требует компонент VBSCRIPT, который Microsoft объявила устаревшим.

| Ключ | Значение | Зачем |
| --- | --- | --- |
| `targets` | `["nsis"]` | один установщик вместо двух |
| `createUpdaterArtifacts` | `true` | рядом с установщиком появляется файл подписи `.sig` |
| `publisher` | `JKNet` | имя издателя в списке программ и ветка `HKCU\Software\JKNet` |
| `category` | `Game` | категория приложения |
| `windows.webviewInstallMode` | `downloadBootstrapper` | установщик не несёт в себе 127 МБ рантайма WebView2 |
| `windows.nsis.installMode` | `currentUser` | установка без прав администратора |
| `windows.nsis.languages` | `["English"]` | язык интерфейса лаунчера тоже английский |
| `windows.nsis.displayLanguageSelector` | `false` | выбор из одного языка бессмыслен |
| `windows.nsis.installerIcon` | `icons/icon.ico` | значок самого установщика |
| `windows.nsis.startMenuFolder` | `JKNet` | группа ярлыков в меню **Пуск** |

Значки всех размеров собирает команда `npm run tauri icon src-tauri/icons/source.svg`. Знак нарисован геометрией без текста: растеризатор шрифтов не видит. Тот же знак лежит в `public/jknet.svg` для вкладки браузера.

Режим `currentUser` ставит программу в `%LOCALAPPDATA%\JKNet`. Папка данных лежит рядом, в `%LOCALAPPDATA%\org.jknet.launcher`: `paths.rs` берёт её у `app.path().app_local_data_dir()` и потому попадает в папку идентификатора, а не в папку имени продукта. Установщик и лаунчер не делят между собой ни одного файла.

Факты об установщике прочитаны в собранном скрипте `src-tauri/target/release/nsis/x64/installer.nsi` версии Tauri 2.11.5. Четыре места решают судьбу файлов на диске.

| Строки | Что делает скрипт |
| --- | --- |
| 35, 48 | `!define PRODUCTNAME "JKNet"` и `!define BUNDLEID "org.jknet.launcher"` |
| 504 | `StrCpy $INSTDIR "$LOCALAPPDATA\${PRODUCTNAME}"` в ветке `currentUser`: путь установки `%LOCALAPPDATA%\JKNet` |
| 758–774 | Деинсталляция удаляет по списку `JKNet.exe`, `resources\trusted_servers.json` и `uninstall.exe`, затем вызывает `RMDir` без ключа `/r` |
| 824, 836–837 | По флажку **Delete app data** скрипт удаляет `$APPDATA\${BUNDLEID}` и `$LOCALAPPDATA\${BUNDLEID}` рекурсивно |

Флажок **Delete app data** совпадает с папкой данных: снятый флажок сохраняет клиенты, библиотеку и настройки, установленный удаляет их вместе с программой (не проверено: деинсталлятор не запускали).

### Как приходит обновление

Раздел `plugins.updater` того же файла задаёт три поля.

| Поле | Значение |
| --- | --- |
| `pubkey` | содержимое файла `jknet.key.pub` целиком, в base64 |
| `endpoints` | `["https://github.com/TrayHard/jknet/releases/latest/download/latest.json"]` |
| `windows.installMode` | `passive` |

Адрес указывает на последний опубликованный релиз репозитория `TrayHard/jknet`. Пока в репозитории нет опубликованного релиза, проверка обновлений отвечает ошибкой: лаунчер пишет её в журнал и работает дальше, потому что неудачная проверка ничего не блокирует.

Порядок работы:

1. Через 5 с после монтирования хук `useAppUpdate` из `src/lib/useAppUpdate.ts` вызывает `check()`. Задержка отдаёт первые секунды окну: экран **Home** в это время грузит список серверов.
2. Плагин скачивает `latest.json`, сверяет версию с версией пакета и возвращает объект `Update` или `null`.
3. Найденную версию показывает уведомление в правом нижнем углу окна. Уведомление рисует компонент `AppUpdateProvider` из `src/components/AppUpdateProvider.tsx`. Он же держит единственную проверку и лежит над маршрутизатором, рядом с `GameEventsProvider`.
4. Кнопка **Install and restart** вызывает `downloadAndInstall`. Обратный вызов приносит события `Started`, `Progress` и `Finished`, из них уведомление собирает полосу загрузки и счётчик байтов.
5. Плагин проверяет подпись пакета и запускает установщик в режиме `passive`. На Windows функция `downloadAndInstall` завершает процесс сама, а установщик поднимает новую сборку: параметр `restartAfterInstall` по умолчанию равен `true`. Вызов `relaunch()` в коде остаётся как документированное окончание для остальных систем.

Карточка **About** на экране **Settings** читает то же состояние через контекст: она печатает установленную версию из `getVersion()` и даёт кнопку **Check for updates**. Проверка при запуске молчит об ошибке и пишет её в журнал. Проверка по кнопке показывает ошибку на карточке: игрок нажал кнопку и ждёт ответа.

Компонент `Toast` из `src/components/ui/Toast.tsx` повторяет одноимённый компонент макета: варианты `info`, `success`, `error`, заголовок, текст и место под действие.

### Две подписи

Подписей две, и они не связаны.

| Подпись | Что подтверждает | Состояние |
| --- | --- | --- |
| minisign плагина обновлений | пакет собран владельцем ключа | работает |
| Authenticode | издателя знает Microsoft SmartScreen | решение не принято |

Без Authenticode SmartScreen предупреждает при первом запуске скачанного установщика. Сертификат стоит денег, а удостоверяющий центр проверяет личность или организацию заявителя. Поэтому вопрос вынесен отдельно. Когда сертификат появится, добавьте в `bundle.windows` поля `certificateThumbprint`, `digestAlgorithm` и `timestampUrl`.

Ключ minisign выпущен командой `npx tauri signer generate` без пароля. Приватный ключ лежит вне репозитория, в `%USERPROFILE%\.tauri\jknet.key`, и в git не попадает: `.gitignore` отклоняет `*.key`. Сборка читает его из переменных `TAURI_SIGNING_PRIVATE_KEY` и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Файл `.env` для этого не годится: бандлер читает только окружение процесса.

Проверки, которые не дают выпустить сломанное обновление, лежат в `src-tauri/tests/updater_config.rs`. Они читают `tauri.conf.json` и требуют включённого `createUpdaterArtifacts`, непустого `pubkey` в форме файла minisign, адреса только по HTTPS и режима установки `currentUser`. Все четыре ошибки одинаково незаметны при сборке и одинаково необратимы после выпуска: лаунчер уже стоит на машинах игроков.

### Выпуск через GitHub Actions

| Процесс | Когда запускается | Что делает |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push в любую ветку, pull request, вручную | пять проверок из [README](../README.md) на `windows-latest` |
| `.github/workflows/release.yml` | тег `v*`, вручную | собирает установщик и создаёт черновик релиза |

Релиз собирает действие `tauri-apps/tauri-action@v1`. Оно вызывает `tauri build`, создаёт релиз с именем `JKNet v__VERSION__` по тегу `v__VERSION__`, прикладывает установщик с файлом подписи и собирает `latest.json`. Файл подписи прикладывает вход `uploadUpdaterSignatures`, манифест — вход `uploadUpdaterJson`; оба по умолчанию включены. Релиз создаётся черновиком: адрес `releases/latest/download/` черновики не отдаёт, поэтому обновление уходит игрокам только после кнопки **Publish release**.

Версии действий взяты из примера страницы [«GitHub Actions» документации Tauri](https://v2.tauri.app/distribute/pipelines/github/) в редакции от 10 сентября 2026 г.: `actions/checkout@v7`, `actions/setup-node@v6`, `dtolnay/rust-toolchain@stable`, `swatinem/rust-cache@v2`, `tauri-apps/tauri-action@v1`. Вход `includeUpdaterJson` из старых руководств в действии версии 1 отсутствует, его заменил `uploadUpdaterJson`.

Порядок выпуска описан в разделе [«Выпуск версии»](../README.md#выпуск-версии).

## Работа без Tauri

Тот же фронтенд открывается двумя способами. Команда `npm run tauri dev` кладёт его в окно WebView2, где работают все API Tauri. Команда `npm run dev` отдаёт его обычному браузеру: этот режим показывает вёрстку и токены без сборки ядра.

В браузере объекта `window.__TAURI_INTERNALS__` нет, и вызов Tauri бросает `TypeError` до того, как успеет отклонить промис. Проверку берёт на себя функция `isTauri` из `src/lib/runtime.ts`. Она закрывает четыре места:

- Обёртки в `src/lib/ipc.ts` отклоняют промис с сообщением `Tauri runtime is not available`. Экраны печатают его в своей плашке ошибки и показывают пустые состояния.
- Кнопки окна в `TitleBar` и подписка на `onResized` ничего не делают.
- Кнопка **Open JKNet folder** остаётся выключенной.
- Перенаправление консоли в журнал не подключается.

## Окно и разрешения

Окно `main` создаётся без системного заголовка: `decorations: false`, размер 1280×800, минимум 1100×700, фон `#0B0E14`. Заголовок рисует компонент `TitleBar`. Атрибут `data-tauri-drag-region` стоит на самой полосе и не наследуется потомками, поэтому кнопки окна остаются нажимаемыми.

Файл `src-tauri/capabilities/default.json` выдаёт окну `main`:

| Разрешение | Зачем |
| --- | --- |
| `core:default` | базовый набор: события, путь, ресурсы, чтение состояния окна |
| `core:window:allow-start-dragging` | перетаскивание за свой заголовок |
| `core:window:allow-minimize` | кнопка свернуть |
| `core:window:allow-toggle-maximize` | кнопка развернуть |
| `core:window:allow-close` | кнопка закрыть |
| `core:window:allow-is-maximized` | иконка кнопки развернуть следует за состоянием окна |
| `core:window:allow-hide` | окно уходит с экрана на время игры при `closeOnLaunch` |
| `core:window:allow-show` | окно возвращается после выхода из игры |
| `core:window:allow-unminimize` | окно, свёрнутое до запуска игры, разворачивается вместе с показом |
| `core:window:allow-set-focus` | возвращённое окно получает фокус |
| `core:event:allow-listen` | подписки экранов **Library** и на события запуска, перетаскивание файлов в окно |
| `core:event:allow-unlisten` | те же подписки при уходе с экрана |
| `dialog:allow-open` | выбор папки `GameData` и файлов pk3 |
| `log:default` | `src/main.tsx` шлёт `console.warn` и `console.error` в журнал |
| `opener:default` | ссылки на JKHub во внешнем браузере |
| `opener:allow-open-path` | кнопка **Open JKNet folder** на экране **Settings** |
| `window-state:default` | сохранение положения и размера окна |
| `updater:default` | проверка, загрузка и установка обновления лаунчера |
| `process:allow-restart` | перезапуск лаунчера после установки обновления |

Разрешение `core:window:allow-is-maximized` входит и в `core:default`: там собраны читающие вызовы окна, включая подписку `onResized`. Список держит его отдельной строкой ради читаемости: так видно, что `isMaximized` вызывает именно `TitleBar`.

Пара `core:event:allow-listen` и `core:event:allow-unlisten` тоже входит в `core:default` и стоит отдельными строками по той же причине. Перетаскивание файлов в окно приходит обычным событием `tauri://drag-drop`, и по списку разрешений это не видно. Ключ `dragDropEnabled` в `tauri.conf.json` не задан: движок включает перетаскивание по умолчанию.

Протокол ресурсов в этом списке не значится намеренно: его включает и ограничивает раздел `app.security.assetProtocol` файла `tauri.conf.json`, а не разрешение. Подробности — в разделе [«Как картинка попадает в окно»](#как-картинка-попадает-в-окно).

Разрешение `opener:default` открывает только ссылки, поэтому у `opener:allow-open-path` своя область: `$APPLOCALDATA`, то есть `%LOCALAPPDATA%\org.jknet.launcher`. Область статична, а `dataDirOverride` задаёт произвольный путь. Если папка данных перенесена, кнопка возвращает ошибку `forbidden path` (не проверено: окно не запускали). Чтобы кнопка работала и там, добавьте новый путь в ту же область.

Плагины подключены в `lib.rs`: `tauri-plugin-log` пишет в `logs\`, `tauri-plugin-dialog` открывает диалог папки, `tauri-plugin-opener` открывает ссылки и папку данных, `tauri-plugin-window-state` восстанавливает геометрию окна, `tauri-plugin-process` перезапускает лаунчер, `tauri-plugin-updater` обновляет его.

Плагины подключены двумя способами. `tauri-plugin-dialog`, `tauri-plugin-opener` и `tauri-plugin-process` встают в цепочку `Builder`. Остальные три подключает `app.handle().plugin(...)` внутри `setup`, каждый по своей причине:

- `tauri-plugin-log` ждёт путь к `logs\`, а путь известен только после того, как `setup` определит папку конфигурации и прочитает настройки.
- `tauri-plugin-window-state` и `tauri-plugin-updater` стоят под `#[cfg(desktop)]`: мобильной реализации у них нет, а зависимость `tauri-plugin-updater` объявлена в `Cargo.toml` для трёх настольных систем.

Состояние `AppState` тоже попадает в приложение из `setup`, вызовом `app.manage`. Вызвать команду до этого нельзя: Tauri выполняет `setup` внутри `build()`, а окно начинает выполнять сценарии только после `run()`, когда цикл сообщений заработает.

Цель `TargetKind::Webview` у журнала не подключена намеренно. Фронтенд сам пересылает консоль в плагин. Такая цель вернула бы те же строки обратно в консоль и зациклила журнал.

Список целей журнала задан методом `targets`, а не `target`. Метод `targets` заменяет список плагина, метод `target` его дополняет. В списке плагина по умолчанию стоит `TargetKind::LogDir`, и эта цель пишет `JKNet.log` в `app_log_dir()`, то есть в тот же `logs\`. Регистр в именах файлов Windows не различает, поэтому `JKNet.log` и `jknet.log` — один файл, и две записи в него удваивали каждую строку журнала.

## Границы и ограничения

- Лаунчер поддерживает только Windows. Код поиска игры собран под `cfg(windows)`, на других системах он возвращает пустой список. Правила отбора архивов рассчитаны на сборки x86 для Windows.
- В сеть ядро ходит по трём путям: HTTPS к GitHub за списком релизов и архивом движка, UDP по IPv4 к мастер-серверам и игровым серверам, HTTP или HTTPS к хабу JKNet. Запросы к JKHub за файлами pk3 появятся вместе с соответствующим модулем.
- Браузер серверов не ищет серверы в локальной сети. Вкладка **LAN** выключена: широковещательный запрос по портам 29070–29073 не реализован.
- Окно с браузером не запускали: события `servers:batch` и `servers:done` проверены только по коду, а разрешение `core:event:default` входит в `core:default` (не проверено запуском).
- Правило «пинг `0` — это бот» проверено по исходникам OpenJK и на живой сети тестом `measures_the_bot_scan`. Сервер с закрытым модом, который переписывает `cl->ping`, покажет бота как человека или наоборот (не проверено: такого сервера в списке не нашли).
- Столбец **PLR** и панель сведений с ботами в окне не смотрели: вёрстка проверена типами, сборкой и рендером пустого экрана в браузере, где команды недоступны (не проверено запуском).
- Политика CSP не задана (`"csp": null`). Задайте `default-src 'self'` после первого запуска окна и проверьте на нём шрифты, стили и вызовы `ipc:`. Директива `img-src` при этом обязана разрешить `asset:` и `http://asset.localhost`, иначе картинки карт перестанут грузиться. Чем позже вы включите политику, тем больше мест ломается за один раз.
- Картинки карт не открывали в окне: индекс, распаковка и уменьшение проверены тестами и запуском `indexes_the_retail_archives`, а протокол ресурсов и `convertFileSrc` — только по документации Tauri (не проверено запуском).
- Первый запуск не открывали в окне: шаги проверены сборкой, типами и вёрсткой в браузере, где команды подменены заглушкой IPC (не проверено запуском).
- Вход через провайдеры JKHub и Discord не работает, пока их администраторы не выдадут OAuth-клиента: хаб отвечает `provider_error`, лаунчер об этом сообщает. Проверен вход через провайдер `dev` и только против заглушки `scripts/mock-hub.mjs`. Против настоящей службы ни один вызов не выполняли (не проверено).
- Экран **Friends** — заготовка. Команды хаба для друзей, присутствия и приглашений реализованы в модуле `hub/`, но вызывающей стороны у них нет.
- Присутствие лаунчер не отправляет: команды над `put_presence` нет, поэтому друзья не видят, что игрок в игре.
- Вход из окна не проверяли: браузер открывает плагин `opener` из Rust, где область разрешений не действует, и это поведение прочитано в исходниках плагина версии 2.5.5, а не наблюдалось (не проверено запуском).
- На экране **Settings** работают папка данных, поле **Extra launch arguments**, кнопка **Run first-time setup again**, карточка **Cache**, карточка **Account** и карточка **About**. Разделы Downloads и Appearance — заготовки.
- Обновление лаунчера собрано и подписано, но ни разу не установлено: релиза по адресу обновлений ещё нет, а установщик не запускали. Проверены сборка установщика и наличие подписи; проверка, загрузка, установка и перезапуск не проверены.
- Установщик не подписан сертификатом Authenticode, поэтому Microsoft SmartScreen предупреждает о нём при загрузке из браузера.
- Перенос данных из старой папки `%LOCALAPPDATA%\JKNet` проверен тестами `paths::tests` на временных папках и одним настоящим запуском `npm run tauri dev` 10 сентября 2026 г.: журнал показал четыре строки `migrated` и одну `left in` про `logs`. На машине с установленным лаунчером перенос не выполняли (не проверено).
